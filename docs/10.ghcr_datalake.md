# NILO datalake: imagen GHCR y VM

Este servicio sigue [09.ghcr_vm_deploy_standard.md](09.ghcr_vm_deploy_standard.md).

La imagen `ghcr.io/neovisionsai/nilo-datalake` incluye la API de archivo y la consola web (`/console`). No hace falta un segundo contenedor de frontend. MinIO va en el mismo `compose.yaml`, con las imágenes públicas `pgsty/minio` y `pgsty/mc`. `minio/minio` ya no existe en Docker Hub. En la VM no se clona el repositorio.

Este archivo no abre MongoDB. Una copia de la base de datos es un fichero en el bucket `nilo-backups`. Las sesiones de captura están en `nilo-media`, bajo `sessions/{id}/`, y el datalake sí se conecta a MinIO para copiarlas.

## Qué hay en el repo

| Pieza | Ruta |
| --- | --- |
| Imagen | `Dockerfile` (sin secretos) |
| Publicación | `.github/workflows/publish-ghcr.yml` |
| Bundle de la VM | `deploy/vm-ghcr/` |

Un push a `main` construye la imagen y la publica. Tags: rama, sha corto y `latest` en la rama por defecto.

## Primera vez en la VM

```bash
sudo apt update && sudo apt install -y docker.io docker-compose-plugin curl
sudo usermod -aG docker "$USER"
# cerrar la sesión SSH y volver a entrar

mkdir -p ~/nilo-datalake && cd ~/nilo-datalake
curl -fsSL "https://raw.githubusercontent.com/NeoVisionsAI/NILO-datalake/main/deploy/vm-ghcr/bootstrap.sh" -o bootstrap.sh
chmod +x bootstrap.sh
./bootstrap.sh
./configure.sh
docker login ghcr.io    # solo si el paquete GHCR es privado
./update.sh
```

Comprobar:

```bash
curl -fsS http://127.0.0.1:8088/v1/health
curl -fsS -o /dev/null http://127.0.0.1:8088/console
```

La consola se abre en `http://<ip-de-la-vm>:8088/`. MinIO (`9000`, `9001`) queda publicado solo en `127.0.0.1` de esa máquina. El puerto `8088` escucha en todas las interfaces para que el hospital abra la consola y para que el backend o el MiniPC envíen datos.

`./bootstrap.sh` arranca MinIO si la contraseña ya está puesta y el puerto `9000` no responde. Si acabas de crear `credentials.env`, entra en `./configure.sh` y elige `m`. La opción `w` abre la consola y prueba el login con el usuario y la contraseña guardados.

Arranque con el sistema, opcional:

```bash
sudo ./deploy.sh --install-systemd
```

## Cada push

En el repositorio: push a `main` y esperar a que el workflow de GHCR termine en verde.

En la VM:

```bash
cd ~/nilo-datalake
./update.sh
```

`./update.sh image` solo descarga la imagen. `./update.sh scripts` solo actualiza los scripts.

## Secretos y la consola

`./configure.sh` escribe `credentials.env` con permisos `600`. El primer arranque copia el usuario de la consola, la clave de ingestión y MinIO a `/data/config/settings.yaml` dentro del volumen. A partir de ahí la consola es quien manda: volver a editar `credentials.env` no cambia un archivo ya creado.

Para repetir esa copia hay que borrar el volumen `datalake`. La contraseña de MinIO solo se aplica al crear su volumen.

El puerto de dentro del contenedor sigue siendo `8088`. `HOST_PORT` en `credentials.env` es el puerto publicado en la VM. En la consola no cambies el puerto de ingestión si quieres que ese mapeo siga valiendo.

## Visibilidad

El repositorio público no hace público el paquete. En GitHub: Packages → `nilo-datalake` → Change visibility → Public, o `docker login ghcr.io` en la VM con un PAT `read:packages`.
