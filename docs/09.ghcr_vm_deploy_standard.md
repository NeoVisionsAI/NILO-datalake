# Estándar de despliegue: GHCR + VM sin código fuente

Documento **genérico** para que cualquier servicio del ecosistema NILO (backend, frontend, lakedata, etc.) siga el **mismo patrón** de publicación y despliegue.

Implementación de referencia: repositorio **NILO-backend**, carpeta `deploy/vm-ghcr/`.

---

## Objetivo

- **Desarrollo:** commit + push a `main` → GitHub Actions construye y publica imagen en **GHCR**.
- **Producción / VM:** un solo comando **`./update.sh`** (scripts + `docker pull` + reinicio). **Sin** clonar el repo ni copiar código a mano.
- **Secretos:** fichero local **`credentials.env`** (nunca en la imagen ni en git).
- **Config no sensible:** puede ir en la imagen (`config.yaml`) o en `credentials.env` / variables de entorno.

---

## Arquitectura

```text
  Repositorio (GitHub)                    GHCR                         VM de despliegue
  --------------------                    ----                         ------------------
  Dockerfile                              ghcr.io/OWNER/SERVICE:tag    ~/servicio-api/
  .github/workflows/publish-ghcr.yml  -->  (imagen con la app)    -->   compose.yaml
  deploy/vm-ghcr/*  (solo scripts)        latest / sha / main          credentials.env
                                                                       update.sh  (1 comando)
```

La **aplicación** vive dentro de la **imagen Docker**.

En la VM solo hay: scripts de operación (~10 ficheros), `credentials.env`, y el contenedor en ejecución.

Servicios externos (Mongo, MinIO, otras APIs) pueden estar en **otro host**; la conexión se configura por env (`credentials.env`), no hace falta desplegar esa infra en la misma VM.

---

## Qué debe crear cada repositorio

Sustituir placeholders:

- `OWNER` — org/usuario GitHub en minúsculas en GHCR (ej. `neovisionsai`)
- `REPO` — nombre del repo (ej. `NILO-backend`, `nilo-frontend`)
- `SERVICE` — nombre del paquete/imagen (ej. `nilo-backend`, `nilo-frontend`)
- `HOST_PORT` — puerto publicado en la VM (ej. backend `8001`, frontend `8080`)

### 1. Dockerfile en la raíz

- Multi-stage si aplica (build frontend + nginx, etc.).
- **No** copiar `credentials.env` ni secretos.
- Exponer el puerto del servicio.

### 2. CI: `.github/workflows/publish-ghcr.yml`

- Triggers: push a `main`/`master`, tags `v*`, `workflow_dispatch`.
- Permisos job: `contents: read`, `packages: write`.
- Login GHCR con `GITHUB_TOKEN`.
- Imagen: `ghcr.io/${{ github.repository_owner }}/SERVICE`.
- Tags: rama, sha corto, `latest` en rama por defecto.
- Build + push con `docker/build-push-action`.
- Opcional: artefacto `SERVICE-vm-ghcr-deploy` con la carpeta `deploy/vm-ghcr/`.

### 3. Carpeta `deploy/vm-ghcr/` (bundle de operación)

Copiar la estructura del backend y adaptar nombres/puertos/imagen.

Ficheros obligatorios:

```text
deploy/vm-ghcr/
  compose.yaml              # servicio con image: ${SERVICE_IMAGE:-ghcr.io/OWNER/SERVICE:latest}
  credentials.env.example   # plantilla de secretos y env (sin valores reales)
  configure.sh              # menú interactivo → genera credentials.env
  deploy.sh                 # docker compose pull + up -d
  bootstrap.sh              # descarga scripts desde raw.githubusercontent.com/.../main/deploy/vm-ghcr/
  update.sh                 # bootstrap + deploy (COMANDO ÚNICO tras cada push)
  sync.sh                   # alias de update.sh
  run.sh                    # alias de deploy.sh (opcional)
  README.md                 # 3 líneas: primera vez + ./update.sh
  nilo-SERVICE-vm.service   # plantilla systemd (opcional)
```

**compose.yaml** mínimo:

- Un servicio (ej. `api` o `web`).
- `image: ${SERVICE_IMAGE:-ghcr.io/OWNER/SERVICE:latest}`.
- `env_file: credentials.env`.
- `ports: "0.0.0.0:HOST_PORT:PUERTO_INTERNO"`.
- `restart: always`.
- Healthcheck HTTP si el servicio lo expone.

**credentials.env.example**:

- Documentar cada variable.
- Comentario: copiar a `credentials.env` o ejecutar `./configure.sh`.
- Incluir solo lo que el contenedor necesita en runtime (URLs de APIs, claves, CORS, etc.).

**configure.sh**:

- Menú para rellenar `credentials.env` (infra, secretos, URLs entre servicios).
- Guardar con permisos `600`.
- Pruebas de conectividad sin descargar imágenes auxiliares absurdas: preferir `curl`, o Python **dentro de la imagen propia** (`docker compose exec` / `run --no-deps`).
- No commitear secretos.

**deploy.sh**:

- `docker compose --env-file credentials.env pull`.
- `docker compose up -d`.
- Flags opcionales: `--install-systemd`, `--foreground` para systemd.

**bootstrap.sh**:

- Descarga lista fija de ficheros de `deploy/vm-ghcr/` desde `main`.
- **No** sobrescribir `credentials.env` si ya existe.
- Actualizar `bootstrap.sh` al final con validación `bash -n`.
- Compatible con `curl | bash`: usar `${BASH_SOURCE[0]:-}` y `NILO_DEPLOY_DIR` / `$PWD`.

**update.sh** (flujo operativo estándar):

```text
./update.sh           → bootstrap (scripts) + deploy (imagen)
./update.sh image     → solo imagen (más rápido si solo cambió código)
./update.sh scripts   → solo scripts (si solo cambió deploy/vm-ghcr)
```

## Visibilidad GHCR

- Repo GitHub **público** no implica paquete GHCR público.
- Primera publicación: Packages → servicio → **Change visibility** → Public, **o** `docker login ghcr.io` en la VM con PAT `read:packages`.

## Flujos operativos

### Primera instalación en una VM (Ubuntu + Docker)

```bash
sudo apt update && sudo apt install -y docker.io docker-compose-plugin curl
sudo usermod -aG docker "$USER"
# cerrar sesión SSH y volver a entrar

mkdir -p ~/SERVICIO-dir && cd ~/SERVICIO-dir
curl -fsSL "https://raw.githubusercontent.com/OWNER/REPO/main/deploy/vm-ghcr/bootstrap.sh" -o bootstrap.sh
chmod +x bootstrap.sh
./bootstrap.sh

chmod +x configure.sh update.sh deploy.sh
./configure.sh          # asistente → credentials.env
docker login ghcr.io    # si paquete privado
./update.sh
```

Comprobar: `curl -s http://127.0.0.1:HOST_PORT/health` (o ruta equivalente del servicio).

Opcional arranque al boot: `sudo ./deploy.sh --install-systemd`.

### Cada commit + push (día a día)

**En el repo:** push a `main` → esperar workflow GHCR en verde.

**En la VM:**

```bash
cd ~/SERVICIO-dir
./update.sh
```

No hace falta `git clone`, ZIP manual ni SCP de código.

### Cambiar secretos o URLs (Mongo, MinIO, API peer)

```bash
./configure.sh    # editar y guardar (menú 10)
./deploy.sh       # recrear contenedor con nuevo env
```

## Conectar con servicios en otro host (patrón backend)

Ejemplo backend: Mongo y MinIO en el **host físico**, API en **VM**.

- Variable tipo **`NILO_INFRA_HOST`** = IP del host **vista desde la VM** (no `127.0.0.1` salvo que la infra esté en la misma máquina).
- Puertos y credenciales en `credentials.env`.
- La imagen de la API no incluye Mongo/MinIO.

Otros servicios pueden usar el mismo idea:

- `API_BASE_URL`, `DATABASE_URL`, `S3_ENDPOINT`, etc. en `credentials.env`.
- Documentar en `configure.sh` qué probar (health de dependencias, ping TCP, o endpoint propio).

---

## Frontend (notas para el agente)

- Imagen típica: build estático + **nginx**.
- URL del backend suele ser **build-arg** (`VITE_*`, `NEXT_PUBLIC_*`) o runtime env según stack.
- Mismo bundle `deploy/vm-ghcr/`; puerto ej. `8080`.
- CORS se configura en el **backend**, no solo en el front.
- Mismo `./update.sh` tras push.

---

## Lakedata / otros workers

- Mismo patrón GHCR + `deploy/vm-ghcr/`.
- Si el servicio no expone HTTP, healthcheck puede ser proceso o script interno.
- `configure.sh` adaptado a sus dependencias (colas, DB, lake storage).

---

## Seguridad

- `credentials.env` en `.gitignore`; permisos `600` en la VM.
- Restringir quién puede `docker pull` si la imagen contiene lógica propietaria.
- Producción: `SEED_USERS=false`, contraseñas fuertes, no usuarios demo.
- No confundir “repo público” con “paquete GHCR público”.

---

## Checklist para un agente que implementa el patrón

```text
[ ] Dockerfile en raíz (sin secretos)
[ ] .github/workflows/publish-ghcr.yml
[ ] deploy/vm-ghcr/ completo (compose, bootstrap, configure, deploy, update, sync)
[ ] credentials.env.example documentado
[ ] configure.sh con menú acorde al servicio
[ ] Imagen GHCR publicada; visibilidad o login documentados
[ ] README del repo: enlace a este doc + comando ./update.sh
[ ] Prueba en VM limpia: bootstrap → configure → update → health OK
[ ] Documentar integración con otros servicios (URLs en configure)
```

## Resumen en una frase

Cada servicio publica **una imagen en GHCR** y entrega **deploy/vm-ghcr/** con **`credentials.env` + `./update.sh`**; en la VM, tras cada push del desarrollador, solo se ejecuta **`./update.sh`**.
